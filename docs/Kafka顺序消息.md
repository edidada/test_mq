# Kafka 顺序消息：原理、配置与示例

> 配套代码见仓库 [kafka/](../../kafka) 目录（Maven 工程，包 com.testmq.kafka）。

---

## 1. 先说结论

**Kafka 只保证「分区（partition）内有序」，不保证「全局有序」。**

所谓「顺序消息」，本质就是三件事共同凑出来的：

1. **同一个业务实体的消息，必须落到同一个分区**；
2. **发送端在重试时不能把消息重排**；
3. **消费端按分区、按 offset 顺序处理，并在处理成功后再提交 offset**。

把这三件做对，就能得到「某个订单 / 某个用户」维度的顺序消息；想要「全集群唯一顺序」，只能把 topic 建成**单分区**（代价是失去并行度、吞吐受限）。

---

## 2. 为什么默认不是全局有序？

一个 topic 通常有多个分区，生产者用分区器把消息分散到不同分区，消费者用多个线程/实例同时消费不同分区。**不同分区之间没有任何顺序约束**，所以跨分区天然无序。Kafka 的设计目标是高吞吐、可水平扩展，全局顺序会和这个目标直接冲突，因此它把「顺序」的粒度下放到分区级别，由使用者按需设计。

---

## 3. 怎么做到顺序消息（三步）

### 3.1 生产者：把同一业务的消息送到同一分区

有三种常见做法：

| 做法 | 怎么做 | 适用场景 |
| --- | --- | --- |
| **用业务 key（推荐）** | 发送时指定 key（如订单号），默认分区器按 hash(key) % 分区数 路由 | 绝大多数「按实体维度有序」需求 |
| **自定义分区器** | 实现 Partitioner，按你的规则（取模、地区、租户）决定分区 | 需要精确控制路由规则时 |
| **单分区 topic** | 建 topic 时只设 1 个分区 | 需要全局唯一顺序、且能接受低吞吐 |

> 仓库示例 OrderPartitioner.java 演示了自定义分区器；OrderedProducer.java 用「订单号作为 key」即可，无需自定义分区器。

### 3.2 生产者：发送端不要重排

发送失败会自动重试，如果同一个分区允许「同时有多个在途请求」，重试可能让后发的消息先到，破坏顺序。对应配置：

- **推荐**：enable.idempotence=true + acks=all。开启幂等后，Kafka 自动把 retries 设为最大值，并保证重试不会重排（此时 max.in.flight.requests.per.connection 仍可保持 5，吞吐不受影响）。
- **旧做法（无幂等时）**：必须把 max.in.flight.requests.per.connection=1，强制同一分区同一时刻只有一个在途请求，才能保序。

另外 acks=all 保证消息被 leader 和 follower 都落盘，避免「丢消息」造成的「漏序」。

### 3.3 消费者：按分区顺序处理 + 手动提交

- 同一个分区内的记录天然按 offset 递增，**必须顺序、同步地消费，不能在单分区内并行**。
- 关闭自动提交：enable.auto.commit=false，改成**处理成功后再 commitSync**。否则：
  - 先提交后处理 -> 崩溃会丢消息；
  - 处理后没提交就崩溃 -> 重启会重复消费（至少不丢，但需业务幂等）。

> 仓库示例 OrderedConsumer.java 按 TopicPartition 逐分区、逐条处理并手动提交 offset。

## 4. 代码演示了什么？

kafka/ 模块模拟「3 个订单，每个订单 5 个有先后关系的步骤」：

- **OrderedProducer**：以「订单号」为 key 发送，每个订单的步骤进入同一分区，保留顺序；并开启 acks=all + 幂等。
- **OrderedConsumer**：订阅 topic，按分区逐个顺序处理，处理完手动提交 offset。
- **OrderPartitioner**：可选自定义分区器，演示如何按规则精确路由（默认分区器对「有 key 的消息」行为与此等价）。

运行（需先有一个可达的 Kafka，详见第 5 节）：

```bash
# 编译
cd kafka
mvn clean compile

# 终端 1：启动消费者
mvn exec:java -Dexec.mainClass="com.testmq.kafka.OrderedConsumer"

# 终端 2：启动生产者（观察日志里同一订单的步骤落在同一分区、且顺序递增）
mvn exec:java -Dexec.mainClass="com.testmq.kafka.OrderedProducer"
```

可用环境变量覆盖连接信息：KAFKA_BOOTSTRAP（默认 127.0.0.1:9092）、KAFKA_TOPIC（默认 OrderTopic）、KAFKA_GROUP（默认 order-group）。

## 6. 常见坑

- **跨分区有序是伪需求**：想要全局顺序就单分区；想要高吞吐就接受「仅分区内有序」，用 key 把相关消息聚到同一分区。
- **消费端并行踩坑**：很多人用线程池并发消费同一个分区的消息，结果把顺序打乱。单分区内一定要串行。
- **只开幂等不够**：还要正确指定 key（否则消息随机分区，顺序无从谈起）。
- **重复消费要靠业务幂等兜底**：即便手动提交 offset，崩溃仍可能重复投递，消费逻辑要能处理重复消息。
