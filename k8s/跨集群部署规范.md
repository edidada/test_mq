# MQ Kubernetes 跨集群部署规范

## 1. 目标与边界

本规范适用于 Kafka、AutoMQ、Pulsar、RocketMQ、RabbitMQ 等消息系统及其
业务客户端。目标是将多集群部署从“多份 YAML”提升为可审计、可回滚、可演练
的交付体系。

这不是将一个消息 Broker 集群拉伸到多个 Kubernetes 集群的规范。跨地域或跨
故障域的网络时延、分区和控制面故障会放大 quorum 型中间件的风险。生产消息
系统应在每个集群内维持独立、本地可用的 Broker 集群；跨集群采用复制、故障
切换和应用级幂等，而不是依赖跨 WAN 的共享 `ClusterIP`。

滴滴公开的云原生实践将 MQ、Redis、ZooKeeper 等有状态服务列为高可用、隔离
和成本需要一并解决的对象；本规范采用同样的“有状态服务优先隔离”原则。
[公开案例](https://qcon.infoq.cn/2020/beijing/presentation/2980)

## 2. 基线架构

```text
Git repository (review, policy, SBOM, manifests)
                    |
             GitOps control plane
                    |
      +-------------+--------------+
      |                            |
cluster-prod-a                 cluster-prod-b / DR
  local MQ                         local MQ
  local applications               local applications
      |                            |
      +---- async replication -----+
                    |
          cluster-test / staging
          isolated test workloads
```

### 2.1 集群职责

| 类型 | 职责 | 禁止事项 |
| --- | --- | --- |
| 管理集群 | GitOps 控制器、策略、集群注册、全局观测聚合 | 承载生产业务 Broker 数据面 |
| 生产集群 | 同地域业务与本地高可用 MQ | 与测试共享节点、共享持久卷或手工 `kubectl apply` |
| 灾备集群 | 独立故障域的热备或温备、复制接收端 | 与主集群共用控制平面、存储故障域或密钥 |
| 测试集群 | E2E、容量、故障注入、版本验证 | 使用生产 Topic、生产凭据或生产 PVC |

集群必须具有稳定且全局唯一的 `cluster-id`、环境、地域、故障域、所有者和
成本中心标签。namespace 名称在需要跨集群服务发现时必须保持一致，并由单一
Git 路径维护。

### 2.2 Namespace 规范

- `middleware`：长期共享的、经容量评审和 SLO 承诺的基础服务；当前仓库的
  单副本 Kafka、Pulsar、AutoMQ-MinIO 持久化验证实例也部署在此处，但不具备生产
  HA 条件。
- `mq-platform`：每个生产集群本地的受管消息中间件，不与普通业务混合。
- `mq-test` 或 `streaming-mq-test`：短生命周期客户端 Job 和故障注入资源。
- `app-<domain>`：业务服务，仅通过受控 endpoint 使用本集群或明确批准的远端
  消息服务。

当前仓库将单节点 Kafka、AutoMQ、Pulsar 的 Broker 数据迁入 `middleware` PVC，
而客户端 E2E Job 保留在 `streaming-mq-test`。这提供了单节点卷重挂载验证，不代表
其具备长期共享中间件的容量隔离和 HA 条件。

## 3. 跨集群通信与数据

### 3.1 服务发现

1. 同集群调用优先使用本地 `Service`，禁止业务代码硬编码 Pod IP。
2. 需要跨集群暴露的无状态服务使用符合
   [MCS API](https://multicluster.sigs.k8s.io/concepts/multicluster-services-api/)
   的 `ServiceExport`/`ServiceImport` 实现，或明确的 L7 Gateway/服务网格。
3. 跨集群服务按相同 `namespace/name` 建模；不得把同名服务用于不同语义。
4. 跨集群入口必须有 mTLS、身份认证、超时、限流、重试预算和熔断；重试只能
   用于幂等操作。
5. 不把 `ExternalName` 当作生产跨集群容灾方案。它没有健康汇聚、流量策略和
   故障切换语义，只能用于短期迁移兼容。

MCS API 的目标是把相同 namespaced service 的后端汇聚成可预测的跨集群服务；
实现可由不同控制器提供，不应在业务 YAML 中绑定某一厂商 CRD。
[SIG Multicluster](https://multicluster.sigs.k8s.io/concepts/multicluster-services-api/)

### 3.2 MQ 数据策略

| 系统 | 跨集群策略 | 不可接受的做法 |
| --- | --- | --- |
| Kafka / AutoMQ | 每集群独立集群；使用复制链路、明确 Topic 白名单、offset 与 ACL 同步策略 | Broker/controller quorum 跨 WAN；所有 Topic 双向无选择复制 |
| Pulsar | 每集群本地 broker/bookie；通过租户、命名空间和 Topic 级 Geo-replication 规划复制 | 将集群间链路当作单集群内部网络 |
| RocketMQ | 每集群独立 NameServer/Broker 组；业务通过双写、Outbox 或受控复制完成容灾 | 以跨集群共享单 NameServer 替代 DR 设计 |
| RabbitMQ | 每集群独立集群；使用 Federation/Shovel 或应用 Outbox，并演练重复投递 | 依赖网络分区下的跨站点镜像队列维持低延迟写入 |

Kafka 官方将 MirrorMaker 2 定义为跨 Kafka 环境的流式复制工具，可复制 Topic、
配置和 Consumer Group offset，适用于容灾、迁移与物理隔离。
[Kafka Geo-Replication](https://kafka.apache.org/42/operations/geo-replication-cross-cluster-data-mirroring/)

所有跨集群消息链路必须定义：

- RPO、RTO、可接受重复窗口和顺序保证范围。
- 主写集群、切换条件、回切条件和防止双主写入的 fencing 机制。
- 全局唯一事件 ID、消费者幂等键、Outbox/Inbox 去重保存期。
- 复制延迟、积压、DLQ 增长和复制错误的告警阈值。

## 4. 交付与变更

### 4.1 GitOps

- Git 是期望状态的唯一来源；集群中的手工变更必须在一个工作日内回写或回滚。
- 每个变更必须通过 PR 审核、清单静态检查、策略检查、镜像漏洞扫描和测试集群
  E2E。
- 使用 Argo CD ApplicationSet、Flux 或等价工具按集群标签选择目标，不在 CI
  中持有所有生产 kubeconfig 并直接 `kubectl apply`。
- Production 同步采用 `manual sync` 或带审批的 promotion；禁止 test 分支直接
  推送生产。
- 回滚使用 Git revert 和 GitOps reconcile，不使用临时手工修改生产对象。

OpenGitOps 将声明式、版本化、自动拉取和持续 reconcile 作为 GitOps 的核心原则。
[OpenGitOps](https://opengitops.dev/about/)
Argo CD ApplicationSet 的 Cluster generator 可从受管集群列表生成目标应用，适合
以环境、地域和角色标签进行选择。
[ApplicationSet generators](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators/)

### 4.2 仓库结构

```text
k8s/
  platform/
    base/                 # PSA、NetworkPolicy、ResourceQuota、监控基线
    clusters/<cluster>/   # 集群特有入口、镜像仓库、存储类和网络差异
  mq/
    base/                 # 每类 MQ 的通用声明，禁止写死 cluster 名称
    overlays/
      prod-a/
      prod-b/
      dr-a/
      test/
  tests/
    e2e/                  # 只包含客户端 Job 与验证脚本
```

`base` 不得包含集群 IP、节点名、私钥、明文密码、`latest` 标签或环境专属
副本数。集群差异通过 Kustomize Overlay、Helm values 或 GitOps 参数化表达。

## 5. 安全与资源准入

### 5.1 必须项

- 镜像使用不可变 digest；SBOM、签名与漏洞扫描作为发布门禁。
- Secret 由外部密钥系统或加密 Git Secret 管理；禁止提交明文、禁止跨环境复用。
- Workload ServiceAccount 最小权限，关闭默认 token 自动挂载，除非运行时确有
  Kubernetes API 访问需求。
- `NetworkPolicy` 默认拒绝，再按 DNS、监控、业务和复制链路最小放行；先确认
  CNI 确实实施 NetworkPolicy，否则声明不会产生隔离效果。
- 业务 namespace 启用 Pod Security Admission：先 `warn/audit=restricted`，完成
  改造后 `enforce=restricted`；基础设施例外必须单独文档化。
- 每个 namespace 配置 `ResourceQuota`、`LimitRange`、`PriorityClass` 和明确的
  CPU/内存 request/limit；MQ Broker 使用专用节点池、污点与容忍，避免与测试
  Job 或不受控业务抢占。

Kubernetes 将 `restricted` 定义为当前 Pod 加固最佳实践的严格级别，建议通过
`warn`/`audit` 逐步推进再 enforce。
[Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/)
NetworkPolicy 与 ResourceQuota 分别控制网络收发和 namespace 资源消耗；网络策略
是否生效取决于 CNI 实现。
[Kubernetes policies](https://kubernetes.io/docs/concepts/policy/)
[NetworkPolicy prerequisites](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

### 5.2 有状态 MQ 附加要求

- 使用 StatefulSet、反亲和、拓扑分布约束、PDB、持久卷、优雅终止与受控滚动
  升级；单节点 Demo 不得复制到生产 Overlay。
- replication factor、min ISR、存储 IOPS、容量水位和 Topic 配额必须按集群独立
  评审。
- TLS、认证、ACL、审计日志和租户配额必须在 broker 层强制，不依赖客户端自觉。
- Broker、控制器、对象存储和元数据服务必须跨节点/可用区故障域部署；备份
  恢复必须在独立集群实测。

## 6. 可观测、SLO 与演练

每个集群必须输出统一标签：`cluster_id`、`environment`、`region`、`zone`、
`service`、`owner`、`cost_center`。跨集群 Dashboard 至少包括：

- Broker 可用性、ISR/副本健康、控制器选举、磁盘水位、网络错误。
- Topic 吞吐、生产/消费延迟、consumer lag、积压时间、DLQ 增量。
- 复制延迟、复制积压、复制失败率、RPO 估算和复制链路证书有效期。
- GitOps 漂移、同步失败、策略拒绝、镜像签名/扫描状态和证书过期。

每季度至少演练一次：单 Broker 故障、单节点故障、单可用区/单集群不可用、复制
延迟扩大、错误切换、回切和数据去重。演练记录必须包含目标 RPO/RTO、实际值、
失败原因和改进项。

## 7. 当前仓库整改顺序

| 优先级 | 工作项 | 验收标准 |
| --- | --- | --- |
| P0 | 保持客户端测试与中间件数据面隔离 | Broker 在 `middleware`，E2E Job 在 `streaming-mq-test`，测试脚本不删除共享 namespace |
| P0 | 镜像固定 digest、移除第三方临时镜像代理依赖 | 测试和生产集群均从受控私有镜像仓库拉取 |
| P1 | 将 `k8s/streaming` 重构为 base/overlay | `test`、`prod-a`、`dr-a` 不复制 YAML，只表达差异 |
| P1 | 增加 ResourceQuota、LimitRange、PSA、NetworkPolicy 和专用节点池 | 策略审计和阻断测试通过 |
| P1 | 为每个 MQ 建立生产 StatefulSet/Operator Overlay | 持久化、PDB、反亲和、TLS、ACL、备份检查齐全 |
| P2 | 引入 GitOps 多集群目标选择和 promotion | 变更可审计、可回滚、无生产手工 apply |
| P2 | 建立跨集群复制与灾备演练 | 主集群失效时按 RPO/RTO 成功切换并回切 |

本规范的第一条执行规则是：先把每个集群内的 MQ 做成可独立生存、可恢复、可
审计的服务，再增加跨集群复制。跨集群不是单集群 YAML 的复制，而是故障域、
身份、数据一致性和交付链路的完整设计。
