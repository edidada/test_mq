# K3s RabbitMQ / MySQL 故障恢复测试报告

## 环境

- 测试时间：2026-10-24（Asia/Shanghai）
- Proxmox：`MiWiFi-RD16-srv`，Proxmox VE 8.4.0
- 集群：现有 K3s v1.35.4，5 个 Ready 节点
- 命名空间：`mq-resilience-test`
- 未创建新的虚拟机，未变更任何既有命名空间或服务。

## 部署内容

- RabbitMQ 3.13-management 和 MySQL 8.4 均以单副本运行在测试命名空间。
- MySQL 使用 2Gi `local-path` PVC `mysql-data`，以保证缩容重建后数据仍然存在。
- 凭据由命名空间内 Secret 随机生成；报告不记录明文。
- Python Job 使用真实 `true_producer.py`、`true_consumer.py`，并将恢复文件写入 Job 的 `/work/runtime`。

## 执行结果

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| 正常收发 | 生产 3 条，消费并落库 | 通过，3 条持久化 |
| MySQL 故障 | 缩容测试 MySQL 至 0；生产并消费 2 条 | 通过，2 条写入 `pending_db.jsonl` |
| MySQL 恢复 | 恢复副本并执行 pending 补偿 | 通过，2 条补偿成功 |
| RabbitMQ 故障 | 缩容测试 RabbitMQ 至 0；生产 2 条 | 通过，2 条写入 `outbox.jsonl` |
| RabbitMQ 恢复 | 恢复副本，确认发布并消费 | 通过，2 条重放并落库 |
| 最终校验 | 检查恢复文件和 MySQL 记录数 | 通过：7 条记录，`outbox.jsonl` 与 `pending_db.jsonl` 均为空 |

控制器最终输出：`K3s resilience test completed successfully`。

## 保留现场

测试脚本默认 `CLEANUP=false`。以下资源目前保留，供后续手动检查：

- 命名空间 `mq-resilience-test`
- RabbitMQ、MySQL Deployment / Service / Pod
- MySQL PVC `mysql-data`
- 测试 Secret 与 ConfigMap
- 节点上已经拉取的 `rabbitmq:3.13-management`、`mysql:8.4`、`python:3.13-slim` 镜像

查看现场：

```bash
ssh k3s-master 'kubectl get deploy,svc,pods,pvc,cm,secret -n mq-resilience-test'
```

重新从头执行演练时使用 `RESET=true bash ./run-k3s-test.sh`。确认不再需要现场后，手动删除：

```bash
ssh k3s-master 'kubectl delete namespace mq-resilience-test'
```

`mysql_native_password` 仅为隔离测试的轻量客户端兼容性启用，不应照搬到生产 MySQL。
